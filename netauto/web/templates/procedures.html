Operational procedures

Two procedures beyond read-only inspection: upgrading device firmware and backing up configuration. Both respect netauto's stance — read-only by default, with a single deliberately gated write.

Firmware upgrade

The Software Upgrade workflow is the one operation that can write to a device. Off unless deliberately armed, it plans the upgrade and produces a runbook, touching nothing.

What it does

connect → snapshot → verify path → [install] → runbook

  1. Snapshot — records the running version and takes a configuration backup, a known-good point to compare and roll back to.
  2. Verify — compares the running version against the recommended target and confirms the upgrade is needed and supported.
  3. Install — the write. Only when armed; the device reboots. Left unarmed, this step is skipped.
  4. Runbook — the version delta, the backup, the exact transfer/verify/install commands, and the rollback plan.

The three gates

The install fires only past all three, each off by default:

1. allow_writesallow_writes: true in config.yaml — currently {{ 'on' if allow_writes else 'off' }}. Gates firmware upgrade only, never a config commit.
2. capabilitythe driver declares the upgrade capability — today only fortinet_cli.
3. confirmationconfirmed with the device name; the workflow does this for you, so it cannot fire by accident.

Procedure

  1. Download the image from support.fortinet.com into firmware/fortiswitch/.
  2. Serve it over TFTP or FTP from a server the switch can reach (the NetAuto host, serving firmware/fortiswitch/).
  3. Plan it first — run Workflows → Software Upgrade with image and server blank, and read the runbook it produces.
  4. Back up the config — the snapshot step captures it; see below to store a sanitized copy.
  5. Arm and run — set allow_writes: true, restart the service, and run the workflow again with the image filename and server IP filled in. The switch validates and reboots into the image.
  6. Verify — after the reboot, run the Configuration Check workflow to confirm the version and that the config survived.

Timing: the install reboots the switch — several minutes of downtime. If the switch is your management path, pick a window where that is acceptable. Rollback: boot the previous image from the switch boot menu; the snapshot backup is the known-good point.

Configuration backup

netauto collects running configuration read-only and stores a sanitized copy — a snapshot and reference, not a restorable backup.

  1. Collects the running configuration over the normal read path.
  2. Sanitizes before writing anything: password hashes, SNMP communities, private keys, certificates and serial numbers are redacted in memory, and the result is verified clean before it is saved.
  3. Stores the sanitized config under configs/.
KindWhereWhy
Sanitized snapshotconfigs/ (committed) Safe to publish; useful for diffing and review
Full restorable backupPrivate repo or offline store Contains secrets — never the public repo

A restorable backup with secrets intact must go somewhere private. The repo .gitignore keeps raw *.cfg and baselines/ out for this reason.
